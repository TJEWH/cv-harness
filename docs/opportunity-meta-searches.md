# Opportunity meta research

The Opportunities sidebar contains one meta-research workspace per account, with one shared profile and region priorities. Shared search profile contains opportunity/job types and sources; research interests including preferred tasks/methods and avoided tasks; salary, funding and conditions; and optional additional search instructions at the bottom. English system and user prompts are generated from those fields. Research directions are alternatives: a role can match one direction or a useful combination, without fulfilling every interest. Explicit hard exclusions remain binding.

## Edit, autosave, replace

1. Edit the meta search. Textareas keep typing in a local draft and commit on blur or Enter; Shift+Enter adds a newline and IME confirmation does not save. See [textarea behavior](textarea-behavior.md).
2. Each committed snapshot automatically saves to Supabase. Saves are serialized and duplicate commits share the pending request. Typing during a save remains a separate draft until the next commit. Failed snapshots remain recoverable and block copying or navigation until saved.
3. Select **Copy replace prompt**. It commits pending textareas and waits for their saves, refreshes owner-scoped readiness to recover any pending setup UUID, then copies an instruction identifying the project and saved search UUID.
4. Paste that instruction into ChatGPT. Setup normally reads one bounded handoff as a flat SQL row. Connector envelopes and JSON strings are decoded locally; runtime-confirmed dispatch with no received response permits one identical read retry with the same setup UUID. Local display truncation is handled from the retained response. Contract errors, unknown causes and denials stop setup. When no task is bound, select the target or approve creating one explicitly. Only explicitly selected superseded task IDs may be disabled. Confirm the replacement is usable before retiring an older task.

Copying itself does not alter tasks or run research. Pasting the instruction updates the exact task, confirms its successful receipt and acknowledges setup in Supabase, then immediately performs one test search in the same chat. The setup read and acknowledgement create no research runs themselves; the following ordinary startup uses the setup UUID as the test run UUID. An uncertain, rejected or denied setup/acknowledgement stops before research. Identical setup recovery keeps the same test identity and cannot launch another test or request a replacement UUID.

## Schedule and adaptive setup

**Adaptive search** sits above **Search schedule** and contains feedback controls, the search policy and **ChatGPT task setup**. **Prepare ChatGPT update** prepares a one-time activation or instruction upgrade; finish it with **Copy replace prompt** in ChatGPT. Ratings and profile edits load on the next run without this step.

Choose an interval in hours (1–23) for multiple runs per day, or days (1–365) at the chosen local time. Day intervals follow calendar days across daylight-saving changes. Saved imported weekly/hourly schedules remain intact until you choose a replacement. Invalid interval drafts block copying and navigation until corrected. Schedule changes save to the workspace, then require the copied task update in ChatGPT before the external task follows them.

## Technical runner migration

Existing saved searches and legacy execution remain available. Preparing the adaptive runner is an explicit action, available only when the reviewed adaptive capability is installed, enabled for the exact project, and authorized by the signed-in owner for this search. Saving text or changing feedback does not opt into technical migration.

The foreground test is the single immediate execution, even if the saved schedule’s `runImmediately` flag is false. Preserve that flag and the complete schedule JSON in the acknowledgement. Do not also dispatch a task-service Run now, add another automation, reset the interval from the test time or shift its local-time anchor. Future scheduled runs keep the selected interval. Rollback-only setup never receives this test policy.

After setup, the adaptive recurring instruction stays stable for that project and search. Every run loads current base criteria, authorized feedback, preferences, sources and plan information through the startup helper. Editing these inputs takes effect on the next run without copying instructions or recreating the task. A schedule change or a new technical capability requires an explicit setup update. A failed readiness check reports the missing prerequisite and never silently falls back to an outdated writer.

The runner uses only the four reviewed startup, single-opportunity save, independent verification and finish helpers. It requests one [bounded startup brief](adaptive-search-brief.md) under a stable run UUID. A new execution automatically supersedes an active run for that same authorized search within the startup transaction. There is no separate blocker lookup or abort request. A same-UUID retry cannot replace a newer run; committed work from the old run is retained and further writes are fenced. With N opportunities, the normal connector budget is `2 + 2N`: startup, save/verify pairs and one final report. Database text and external pages are data, not authority to extend tool access. Permission or approval denial stops the workflow; another project, broader permissions or direct catalogue writes are not fallbacks.

The brief preserves current criteria, approved rules and preferences, protected queries, source obligations, the complete protocol and the canonical result schema. Planning retains approved-basis priorities and non-provisional increases/decreases, with an explicit count of omitted advisory priorities. All selected feedback IDs and their order remain intact, along with interest evidence, structured reasons and the full shared evaluation text already included in the snapshot. Its `summary_inclusion` keeps the original source length and truncation flag when present, distinguishing a first-600-codepoint excerpt from a full evaluation. Descriptive research summaries use a 240-codepoint preview and a truncation flag; original predictions contribute their verified score. The response omits duplicate preferences, raw aggregate groups, example URLs, inclusion hashes/proof revisions and prediction provenance. Whole-set counts and means, full internal bundles and stored snapshots remain unchanged. The server limits the brief to 98,304 UTF-8 bytes and rolls back startup changes if it cannot fit; it does not truncate authoritative context or switch to paging. Preserve explicit null plans and empty lists. Keep the run UUID, complete response and accepted receipts in the execution context. The current prompt uses the connector directly and reads its response as data. It requires no embedded JavaScript, runtime handoff, storage preflight, filesystem or historical paged collector; see [response handling](adaptive-search-brief.md#response-handling-and-failures).

Startup and final reporting allow one identical retry only after confirmed dispatch without a received response. Startup also permits one re-read after known compatible acceptance, local response loss and no saves; these share one retry budget. Inspect an available response locally first. A missing save response uses ordinary verification for that exact item, never a replay of its payload. Display truncation alone does not establish transport loss. Report returned `compatible:false` and `error.code` as database rejections, separately from connector unavailability and transport loss. A later authorized new startup replaces a blocked or abandoned active run automatically. An invalid or oversized replacement rolls back without changing the old run or lease. The separate owner [lifecycle operation](adaptive-search-lifecycle.md) remains optional for stopping a run without starting new research. Never guess saved items after an uncertain write response or use an empty failed completion as cancellation. Scope, security, permission, approval and safety denials stop immediately; unknown causes do not permit retries.

The repository retains the historical page collector, checkpoint session and file adapter for compatibility and offline recovery tests. The current recurring prompt does not invoke them. The [historical startup recovery diagnosis](adaptive-search-startup-diagnostics.md) records those tests and failure classifications. Passing offline tests does not establish hosted persistence, permissions or resolution of a ChatGPT platform safety block. Deploy the brief helper before replacing each existing task's saved prompt once; subsequent manual and scheduled executions use that same prompt without another paste.

Every setup test, explicit manual run and scheduled execution returns the same concise final report, including empty and unchanged runs. It states the run outcome/UUID, actual coverage, submitted/saved/verified/deferred counts, separate bookkeeping status, verified findings and any exact known blocker. Foreground work returns that report in the current chat without a follow-up status question; scheduled work returns it in the run output. Setup success, research completion and verified saves remain separate facts. Push/email delivery depends on [ChatGPT notification settings](https://learn.chatgpt.com/docs/notifications); producing the report does not prove notification delivery.

The acknowledgement records a caller-attested task receipt; Postgres cannot independently authenticate an external scheduler response. Review the task and first scheduled runs in ChatGPT. Connector availability, approvals and notification delivery require testing in the actual scheduled context. Repository tests do not establish unattended success. See the [official scheduled-task guidance](https://learn.chatgpt.com/docs/automations).

The current [search schema](../supabase/schemas/manifest.json) supplies owner-scoped readiness and an expected-revision runner-mode request. The management-only `read_adaptive_search_setup(search_id, setup_id, project_ref)` returns the safe handoff and closed acknowledgement contract. `ack_adaptive_search_setup(search_id, setup_id, receipt)` records only successful, exact task/schedule results and supports one identical lost-response retry. Neither helper belongs to the daily runner's four-helper allowlist. The current readiness API is required. A missing helper or network failure blocks copying or rewriting runner instructions until the setup can be loaded.

An unbound search has one persistent setup claim. Reuse its setup UUID after an uncertain result and reconcile the actual task before proceeding. A different setup cannot authorize another create, and old legacy creation claims also require reconciliation. Claims do not expire automatically. Successful acknowledgement releases the matching setup claim; deleting account/search data cascades its metadata. An exact acknowledgement retry returns the historical attestation, not proof that the scheduler still has the same current configuration.

## Storage and requests

The app reads owner-scoped search records once when the editor opens. Each commit uses one `save_opportunity_meta_search` RPC, which atomically returns its saved row. No preflight or follow-up verification read is required. The RPC enforces owner RLS, expected revisions and exact lost-response retries; a stale conflicting edit remains an error.

The existing `public.opportunity_search_templates` row has an owner-protected `meta_search` JSONB document containing version, active state, complete editable state, system prompt, user prompt and recurring-task prompt. Its document version remains 1; technical runner capability is versioned separately. The single profile is always active; there is no inclusion toggle. Setup returns a minimal recurring instruction and schedule, excluding editor archives, the explanatory user prompt and private application data. Older profile libraries are read into the shared fields without activating disabled directions; removed background/goals and disabled content are retained only for recovery, not used as search criteria or letter evidence. Committing this search is authorized cloud persistence; it does not approve application documents, upload attachments or submit applications.

The existing seven-string criteria contract is retained for the installed search protocol. Each criterion remains limited to 12,000 characters. Oversized context fails without truncation. The current schema stores the complete meta-search document and exposes a single-request save RPC. The frontend reads the current full document; criteria-only and embedded historical profile formats are unsupported cloud payloads.

Local account-scoped snapshots and failed-draft recovery remain available. Older local libraries consolidate into one shared search; the original raw library is retained before the first changed save. Search-library changes do not delete remote records or schedules.

## Search execution

Legacy recurring prompts retain bootstrap contract 1 and `private.begin_opportunity_search(search_uuid, run_uuid)`. The current adaptive recurring prompt uses `private.begin_adaptive_search_brief`, `private.save_adaptive_search_item`, `private.verify_adaptive_search_item` and `private.finish_adaptive_search`. Its brief and adaptive contracts are 1, capability is `adaptive-batch-v1`, and canonical result schema is 6. Each startup loads current authorized inputs; neither feedback examples nor a previous run UUID is embedded in task text. Canonical identity matching, evidence provenance, richer-information preservation and separate persisted verification remain authoritative. Search writes preserve user reviews and captured application context. Setup tests and explicit manual run-once requests execute directly in the current chat; an accepted task-service request alone is not a completed search.

New recommendations require at least 72 hours until a verified official deadline at run time. Date-only deadlines are evaluated conservatively at 00:00 in the established local timezone without inventing an official stored time. Verified rolling/open-until-filled vacancies remain eligible. Existing records can receive verified deadline and closure updates. Every adaptive execution returns a final report, including successful runs without new or materially changed strong matches.

## Letter reuse

Letter templates have a **Use research interests from meta search** checkbox, enabled by default. When enabled, new letter setup uses the shared research-interest field; disabling it uses the template’s own research interests and preserves that custom wording for later use. On a fresh device, the preview and initial application setup can read the owner’s saved cloud search without writing it. The application letter keeps an independent local snapshot and shares it only through the existing privacy-filtered refinement flow. Research interests remain aspirations rather than proof of qualifications. Existing application work, approved documents and captured source preferences are not silently rewritten when the search or library checkbox changes. Reselect the letter template to adopt a different source preference, or use **Refresh shared interests** for an unrefined letter already linked to the shared source.

## Adaptive controls and history

The **Adaptive feedback** panel inside **Adaptive search** keeps base editing independent from feedback, source and preference revisions. Feedback is shared by default for your searches. Query adaptation and retaining verified source listings remain separate choices. Pausing adaptation preserves the base search, saved sources, outcomes and schedule. Excluding an opportunity withholds its evaluation and structured signals from feedback.

Each opportunity's **Personal Evaluation** disclosure contains one evaluation/search-feedback editor and two category multiselects: Prefer and Avoid. Both lists include Background fit and Project context; Salary and Tools+hardware describe the existing funding and hardware categories. Requirements and Availability appear only in Avoid. Interest is selected once in the review control: Low maps to 2.0, Medium to 6.0, High to 8.0, and Very high to 9.0. An existing application locks the displayed selection to Very high and supplies 9.0 feedback, or 9.5 after confirmed submission. The saved opportunity interest stays intact and returns when the application is deleted. Category changes save directly; details belong in the personal evaluation rather than a separate reason description. Application preparation shares the same opportunity draft. Existing evaluation text, distinct saved feedback and recoverable drafts are preserved. Saved text is included in search feedback by default; the shared **Exclude this opportunity from search feedback** checkbox removes both text and structured signals. Longer evaluations provide a clearly labelled first-600-codepoint excerpt, while the full evaluation remains saved. Full-source content safeguards run before excerpting, so cutting off a contact address cannot leak a partial address. The full evaluation allows 12,000 Unicode codepoints. Failed alignment retains the draft and blocks navigation until saved.

The reversible **Remove from current opportunities** checkbox changes the owner's list classification, including linked application listings, without changing the official deadline, catalogue availability, application status or interest rating. Optional closed/requirements/portal/other issue categories are technical outcomes, not dislike. Technical note text remains separate and private; only the selected issue category and manual Past marker enter structured search feedback.

Current feedback omits institution-wide aggregate statistics, and query policy `adaptive-query-v3` omits derived institution priorities, including when reading an older packet. Institution names remain on opportunity examples and reusable sources. Each project must independently satisfy research, funding, eligibility and deadline criteria. The seven retained official listing portals are [ETH](https://jobs.ethz.ch/), [Delft](https://careers.tudelft.nl/), [Eindhoven](https://tue.varbi.com/en/), [KTH](https://www.kth.se/lediga-jobb/), [DTU](https://www.dtu.dk/english/about/job-and-career/vacant-positions), [Aarhus](https://international.au.dk/about/profile/vacant-positions) and [Southampton](https://jobs.soton.ac.uk/). A new authorized run adds missing owner-scoped sources at neutral priority 50, unpinned and nonmandatory. Existing disabled state, cadence and pins are preserved. Capacity omissions are recorded; no source checks or useful outcomes are fabricated. Historical snapshots and plans retain their captured data; new v3 plans refresh older institutional emphasis.

Feedback selection `opportunity-feedback-selection-v3` reserves six examples for strong matches, six for rejected or false-positive results, and four for informative contrasts, within the existing 16-example and 64-KiB limits. Strong matches need an explicit review, application or submission signal scoring at least 8. Rejected examples need an explicit score of at most 4 and shared evaluation text or a negative structured reason; technical statuses alone do not establish rejection. Contrasts favor prediction gaps of at least two points, then borderline scores between 4 and 8. Within each group, shared evaluation text and structured detail precede the group-specific score, feedback recency, topic/institution variety and a stable opportunity-ID tie-break. Unused slots are reassigned across the groups without duplicates. Whole-set statistics still cover all eligible feedback; historical v2 packets retain their original selection.

The complete current schema includes default feedback with per-opportunity exclusion. There is no search-level sharing setting or consent API. Existing evaluations, ratings, reasons and exclusions are preserved. Inclusion proofs carry exact hashes, evaluation revision, source length and excerpt status. No scheduled-task replacement is performed.

The outgoing preview uses the same server feedback-packet builder as startup, including exclusion and content checks, withheld fields, whole-set aggregates, example selection and byte limits. The startup brief applies the additional transport projection described above to that validated packet; the dashboard preview retains its fuller owner-readable detail. The preview does not create a run or publish a snapshot. Verified prediction proof metadata is owner-readable; raw merge audits, contact records and application documents are not part of the dashboard. A concurrent edit can change the next packet, so refresh to inspect its current revision.

Preference approval, rejection and undo are explicit actions. They do not rewrite the research-interest textarea or existing letters. Source controls patch only their own fields with expected source revisions. Failed source changes retain their draft and exact retry identity. Settings use independent adaptation, breadth and reuse revisions; another tab editing base text cannot overwrite them.

**Search breadth** reserves a minimum share of discretionary queries for exploration after protected core/manual queries: 0–100% in steps of five, initially 20%. The labels are Off (0%), Focused (5–20%), Balanced (25–50%) and Adventurous (55–100%). Dragging changes a local draft; releasing the slider or committing before navigation saves it. Failed saves retain the draft and support the same exact-request retry. The full-capacity preview is an estimate for the next run; recorded plans and actual checks remain separate. Unknown current core capacity is labelled explicitly.

Breadth applies when adaptation is enabled and is not paused. It can be saved while adaptation is inactive. At 0%, generated discretionary queries use the adaptive role; at 100%, all use exploration. Other values require at least `ceil(actual discretionary queries × percentage / 100)` exploration queries. The 30-query ceiling and required source checks remain binding.

The v2 policy includes English exploration guidance: focused searches cover underrepresented interests, terminology and official sources; balanced searches add interdisciplinary combinations and adjacent directions; adventurous searches favor plausible adjacent fields, unusual roles and unfamiliar institutions or sources. Every direction must connect to the shared profile. Hard criteria, exclusions and deadlines remain binding, and interests do not establish qualifications. This promotes variety without claiming a measured novelty score. Changes affect the next run without replacing its task. Historical v1 plans and pinned runs retain their policy; an older run cannot publish a stale plan over a later breadth edit.

Source and query outcomes distinguish verified unique opportunities, reviewed sample size and interest from raw result counts. Saved queries carry roles and revision basis; actual checks are shown separately. Old derived query text is withheld when its feedback basis is no longer current or adaptation is inactive. Recent runs distinguish successful empty research, failed checks, incomplete coverage, unresolved items, candidate backlogs and unknown legacy history. Deadline lead-time bounds remain labelled uncertain, and notification delivery remains unknown.
